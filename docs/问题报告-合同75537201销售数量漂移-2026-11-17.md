# 问题报告：合同 75537201 销售数量每次查询结果不一致

**日期**：2026-11-17
**环境**：百购 ERP · `192.168.0.120:1543` · 库 `RDS_SC`
**报表对象**：`商品销售_含任务` 查询（租户 8，机构 1303001，2026-11-10 ~ 2026-11-16）
**现象**：同一入参、同一条 SQL，每次执行「合同 75537201」的 **销售数量** 都不同；销售金额始终不变。

---

## 一、结论（一句话）

问题不在你写的 SQL 聚合逻辑，而在他引用的数据库视图 **`dbo.vw_gds_sale_record`**：
该视图用 `ROW_NUMBER() ... ORDER BY a.c_au_dt DESC` 去重，但**排序键不唯一**，导致同一天同一商品的多行明细里，SQL Server 每次随机挑一行，结果随执行计划漂移。

修复方式：**不再 JOIN 这个视图**，改为直接聚合明细表 `tb_io_sale_record` + `tb_io_sale_record_g`，并排除「退货录入」行。

---

## 二、复现证据

同一入参、同一条 SQL，连跑 5 次：

| 次数 | 合同 75537201 销售数量 | 销售金额 |
|---|---|---|
| 1 | 592.000 | 18018.77 |
| 2 | 595.000 | 18018.77 |
| 3 | 509.000 | 18018.77 |
| 4 | 938.460 | 18018.77 |
| 5 | 1057.460 | 18018.77 |

- 金额恒定，**只有数量在漂**
- 业务确认：**1358.460 才是正确答案**

修复后同样连跑 10 次：**恒定 1358.460**（详见第五节）。

---

## 三、根因：`vw_gds_sale_record` 视图定义有缺陷

### 3.1 视图原始定义（`RDS_SC`）

```sql
CREATE VIEW [dbo].[vw_gds_sale_record]
AS
SELECT t.c_tenant_id, t.c_store_id, t.c_sale_da, t.c_con_no,
       t.c_gcode, t.c_count, t.c_n_sale
FROM (
    SELECT a.c_tenant_id,
           a.c_store_id,
           b.c_sale_da,
           b.c_con_no,
           b.c_gcode,
           b.c_count,
           b.c_n_sale,
           ROW_NUMBER() OVER (
               PARTITION BY a.c_tenant_id, a.c_store_id, b.c_sale_da, b.c_gcode
               ORDER BY a.c_au_dt DESC          -- ★ 缺陷所在：排序键不唯一
           ) AS c_sort
    FROM dbo.tb_io_sale_record a (NOLOCK)
    JOIN dbo.tb_io_sale_record_g b (NOLOCK)
      ON a.c_tenant_id = b.c_tenant_id
     AND a.c_id = b.c_id
    WHERE a.c_status = '3'
) t
WHERE t.c_sort = 1;   -- 每(租户,门店,日期,商品)只保留 1 行
```

### 3.2 缺陷一：排序键 `c_au_dt` 存在并列 → 结果不确定

`PARTITION BY (租户, 门店, 日期, 商品)` 内部可能有多行，`ORDER BY a.c_au_dt DESC` 是**唯一**的排序依据。当多行的 `c_au_dt`（审核时间）完全相同时，`ROW_NUMBER()` 的排序就是**不确定的**——SQL Server 不保证任何顺序，执行计划稍变（并行度、缓存、参数嗅探）挑中的行就变。

实测（租户 8，11/10–11/16）：

| 指标 | 数值 |
|---|---|
| 参加去重的键组总数（门店×日期×商品） | 3572 |
| 组内多于 1 行的 | 84 |
| 其中 `c_au_dt` 完全相同（真并列） | **18 组 / 36 行** |
| 跨合同组 | 0 |
| 多单据组 | 66 |

其中 1303001 门店就占 10 个并列组，所以它漂得最厉害。

### 3.3 缺陷二：去重粒度错——同一张单据里同一商品会有多行

`tb_io_sale_record_g`（销售明细）一张单内，同一商品可以有**多行**，靠 `c_sort`（顺序号 / 行号）区分。合同 75537201 / 商品 7001183 的实际数据：

| 单号 | c_sort | 数量 | 金额 | 通道 | 备注 |
|---|---|---|---|---|---|
| 20261110000236 | 1 | **239.460** | 3592.51 | xxxs | |
| 20261110000236 | 2 | **-8.000** | -239.46 | xxxs | **退货录入** |

**两行的 `c_au_dt` 完全相同**（2026-11-10 21:06:38）。

视图把「正常销售行 + 退货行」当成「需要去重的重复数据」，`ORDER BY c_au_dt` 又区分不了它们 → **每次随机保留正常行或退货行**：

- 抽到 `c_sort=1`（正常销售）→ 数量偏大
- 抽到 `c_sort=2`（退货行）→ 数量偏小甚至为负

全库这 18 个多行组合，**100% 都含 `c_sort=1` 行**，全部是「同一商品多行明细」，不是重复单据。

### 3.4 ⚠️ 重要澄清：`c_sort` 不是退货标记

`sys.columns` 里 `c_sort` 的字段注释就是「**顺序号**」，它是单据内的行号。实测证明：

| c_sort | 备注 | 数量符号 | 行数 | 数量合计 |
|---|---|---|---|---|
| 1 | （空） | 非负 | 3514 | 195614.670 |
| 2 | （空） | **非负** | **17** | **173.000** |
| 2 | 退货录入 | 负 | 8 | -19.000 |
| 3 | （空） | 非负 | 4 | 4.000 |

有 17 行 `c_sort=2` 其实是**正数正常销售**，例如单据 20261110000121：

| c_sort | 商品 | 数量 | 金额 |
|---|---|---|---|
| 1 | 7000503 | 1 | 6344.00 |
| 2 | 7000504 | 1 | 2724.00 |
| 3 | 7000505 | 1 | 580.00 |

这是同一张单卖了三件不同商品，`c_sort` 只是行号。

**因此：绝不能按 `c_sort=1` 过滤**，那会丢掉真实的 17 行销量。识别退货只能靠「备注 = 退货录入」或「数量为负」。

### 3.5 缺陷三：会把「多张单据」误当成重复数据吞掉

同一（门店、日期、商品）如果有多张不同单据，视图的 `PARTITION BY` 也会去重掉：

| 门店 | 多单据组数 | 涉及数量 |
|---|---|---|
| 1301001 | 10 | 12.00 |
| 1301002 | 3 | 33.00 |
| 1303001 | 32 | 2940.79 |
| 1303021 | 21 | 1756.04 |

典型案例 商品 7000565，同一天三张单：

| 单号 | sale_type | 数量 | 金额 | sale_id |
|---|---|---|---|---|
| 20261113000034 | 411 | +1 | 1354.91 | BL126111300000025 |
| 20261113000044 | 421 | **-1** | -1354.91 | BL126111300000034（冲销） |
| 20261113000045 | 411 | +1 | 1354.91 | BL126111300000035（重开） |

411=正常销售、421=冲销单。视图只留一张 → 结果随机为 +1 / -1。

### 3.6 各口径对照（合同 75537201 / 商品 7001183，一周合计）

| 口径 | 销售数量 |
|---|---|
| **排除「退货录入」行（本次采用）** | **1358.460** ✅ |
| 仅 `c_sort=1` 行 | 1358.460（本例恰好相同，但全库会误伤 17 行） |
| 全部明细行合计 | 1340.460 |
| ERP 汇总表 `tbs_sd_gdsprv.c_n` | 1365.460 |
| 视图 `vw_gds_sale_record`（随机） | 592 / 595 / 509 / 938.46 / 1057.46 … |

> 金额 18018.77 三种口径都一致——说明**金额路径是干净的，只有数量路径有问题**。

## 四、具体到 SQL 行号

以你发来的原始 SQL 为准（含开头的 `DECLARE` 块）。

### 4.1 问题源头：第 192 行

```sql
LEFT JOIN vw_gds_sale_record k ON a.c_tenant_id = k.c_tenant_id AND a.c_store_id = k.c_store_id AND a.c_gcode = k.c_gcode AND a.c_con_no = k.c_con_no AND a.c_fact_da = k.c_sale_da
```

这**一行**就是全部问题所在。它引入了那个有缺陷的视图。

### 4.2 受影响的取值列：第 76–78 行

```sql
	   SUM(k.c_n_sale) AS 销售数量,                                                     -- 第 76 行 ← 直接受影响
	   SUM(k.c_count) AS 交易笔数,                                                      -- 第 77 行 ← 直接受影响
	   IIF(SUM(k.c_count)=0,0,ROUND(SUM(a.c_sale_value - a.c_disc_value) / SUM(k.c_count),2)) AS 客单价,  -- 第 78 行 ← 被连带影响
```

- 第 76 行 `SUM(k.c_n_sale)`：**结果漂移的直接表现**
- 第 77 行 `SUM(k.c_count)`：交易笔数同样漂移（明细笔数也来自被去重后的行）
- 第 78 行：客单价分母用了 `k.c_count`，所以客单价也跟着漂

**不受影响**：
- 第 75 行 `SUM(a.c_sale_value - a.c_disc_value) AS 销售金额` —— 金额来自 `a` 侧（`tbs_sd_gdsprv`），与视图无关，所以恒定 18018.77。

### 4.3 数据量核查（已确认安全，无需改动）

| 检查项 | 结果 |
|---|---|
| `tb_md_gds` 商品主档 (tenant, gcode) 重复 | 0 |
| `tb_depart` / `tb_md_gdsclass` / `tb_md_brand` / `tb_md_partner` 重复键 | 各 0 |
| `tb_md_contract` (合同, 版本) 重复 | 0 |
| `tb_md_plan` 同(机构,合同,周期)多行 | 0 |
| `(tenant, c_id, c_sort)` 明细唯一 | 0 重复 |

这些关联都不会放大行数，**不用动**。

## 五、修复方案

### 5.1 改动（替换原第 192 行）

**删掉**原来的 `LEFT JOIN vw_gds_sale_record k ...`（第 192 行），**换成**：

```sql
LEFT JOIN (
		SELECT x.c_tenant_id, x.c_store_id, x.c_sale_da, x.c_gcode, x.c_con_no,
		       SUM(x.c_n_sale) AS c_n_sale, SUM(x.c_count) AS c_count
		FROM (
			SELECT r.c_tenant_id, r.c_store_id, g.c_sale_da, g.c_gcode, g.c_con_no, g.c_n_sale, g.c_count
			FROM dbo.tb_io_sale_record r WITH (NOLOCK)
			JOIN dbo.tb_io_sale_record_g g WITH (NOLOCK) ON r.c_tenant_id = g.c_tenant_id AND r.c_id = g.c_id
			WHERE r.c_status = '3'
			  AND r.c_tenant_id = @tenantid
			  AND ISNULL(g.c_note,'') <> '退货录入'                -- ★ 排除退货行（按业务确认：退货不计入销量）
			  AND g.c_sale_da >= @查询日期__sdt
			  AND g.c_sale_da <= @查询日期__edt
		) x
		GROUP BY x.c_tenant_id, x.c_store_id, x.c_sale_da, x.c_gcode, x.c_con_no
	 ) k ON a.c_tenant_id = k.c_tenant_id AND a.c_store_id = k.c_store_id
	    AND a.c_gcode = k.c_gcode AND a.c_con_no = k.c_con_no AND a.c_fact_da = k.c_sale_da
```

其余部分**一行都不用动**（金额、任务、完成率、分组维度全部保持原样）。

### 5.2 为什么这样改是对的

| 要点 | 说明 |
|---|---|
| **无 `ROW_NUMBER`，无不确定排序** | 纯 `GROUP BY` 聚合，SQL Server 结果天然确定 |
| **不做无意义的去重** | 明细行本来就该全部累加，不存在「重复数据」问题 |
| **只排除退货行，保留真实多行** | 用 `c_note <> '退货录入'` 而不是 `c_sort=1`，不会误伤 17 行正数销售 |
| **主键粒度匹配** | 输出粒度 (租户,门店,日期,商品,合同) 与 JOIN 条件完全对齐，不会放大行数 |
| **不改数据库对象** | 视图 `vw_gds_sale_record` 是 ERP 核心对象，被 7 个存储过程引用，不动它 |

## 六、需要知道的两个遗留问题

### 6.1 交易笔数口径

你确认「退货不计入销量」，但**交易笔数**要不要也排除退货？本次修复中，退货行的 `c_count` 也一并排除了。如果业务上「交易笔数」希望包含退货笔数，需要单独处理。

### 6.2 金额与数量口径不一致

- **销售金额**（第 75 行）：来自 `tbs_sd_gdsprv.c_sale_value - c_disc_value`，**已含退货**（负数冲减）
- **销售数量**（第 76 行）：修复后**不含退货**

同一行数据里金额含退货、数量不含退货，`客单价 = 金额 / 笔数` 会略偏高。如果要求两者一致，需要决定是统一含退货还是统一不含。

## 七、建议向 ERP 厂商反馈

`vw_gds_sale_record` 的这个缺陷会影响**所有**使用它的报表（当前 7 个存储过程 + 外部报表）。建议要厂商修：

```sql
-- 最低限度：加确定性 tie-break，保证结果可重复
ROW_NUMBER() OVER (
    PARTITION BY a.c_tenant_id, a.c_store_id, b.c_sale_da, b.c_gcode
    ORDER BY a.c_au_dt DESC, b.c_sort ASC, a.c_id DESC   -- 加后两个
) AS c_sort
```

但**根本修法是改语义**：这视图应该是「按单据聚合」而不是「按商品去重」，现在的实现会吞掉多单据和同单多行。
