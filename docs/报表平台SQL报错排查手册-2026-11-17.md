# 报表平台 SQL 报错排查手册：为什么 Navicat 能跑、平台报语法错误

**日期**：2026-11-17
**场景**：百购 ERP 报表平台，给「商品销售（含任务）」报表加 9 个计算列
**结论来源**：实测。同一条 SQL，Navicat 执行成功，平台报 `")"附近有语法错误` + `关键字 'AND' 附近有语法错误`

---

## 一、核心结论（先看这段）

> **平台会「解析并改写」你的 SQL，而不是原样丢给 SQL Server。**
>
> 它只擅长处理**结构简单**的语句。一旦你在**最外层 SELECT 列表**里写复杂表达式
> （多层函数嵌套 / 聚合之间的除法 / 窗口函数），解析器就会被拆坏，
> 报出一堆 `")"附近有语法错误` 这种和自己 SQL 对不上的错。

**所以：Navicat 能跑 ≠ 平台能跑。这不是你的 SQL 有问题，是平台解析器脆弱。**

---

## 二、这次的排查过程（可直接照抄的方法）

### 第 1 步：确认 SQL 本身没毛病

```
Navicat 执行成功  →  SQL Server 认可，语法正确
平台报错          →  问题在平台的解析环节
```

**这一步很重要**：先排除「我写错了」，再往平台身上找。否则会一直在改自己的 SQL。

### 第 2 步：读错误信息，但不要照字面理解

这次报的是：

```
")"附近有语法错误。  关键字 'AND' 附近有语法错误。
")"附近有语法错误。  ")"附近有语法错误。
```

三个 `")"` 错误 + 一个 `AND` 错误。

**关键判断**：把 SQL 逐层括号数一遍，如果括号完全配平，那这些 `")"` 报错就是
**解析器自己拆坏了**，不是你少写括号。别去补括号，补不出来的。

### 第 3 步：两次修改都报同一个错 → 说明找错方向了

第一版怀疑是这两个：

| 怀疑对象 | 处理 |
|---|---|
| `SUM(SUM(x)) OVER (PARTITION BY ...)` 嵌套聚合 + 窗口 | 改成预聚合临时表 |
| `BETWEEN ... AND ...` 在 ON 条件里 | 改成 `>=` 和 `<=` |

改完**报错一模一样**（连顺序和个数都一样）→ 说明这两个都不是根因。

> 🔴 **经验：平台报错如果同一次修改后一字不差，说明你动的地方它根本没读到。
> 它在更早的阶段就挂了。**

### 第 4 步：换思路 —— 对比「能跑的」和「不能跑的」

手上有两份能跑的证据：

**证据 A：原 sqlB 能跑**，它最外层 SELECT 的复杂列长这样：

```sql
IIF(SUM(k.c_count)=0,0,ROUND(SUM(a.c_sale_value - a.c_disc_value) / SUM(k.c_count),2)) AS 客单价
```
→ 函数嵌套 3 层

**证据 B：sqlA 能跑**，它的完成率长这样：

```sql
-- 最外层 SELECT
CONVERT(VARCHAR(20), CAST(ROUND(t.[月度任务完成率] * 100, 1) AS DECIMAL(10,1))) + '%' AS 月度任务完成率
--                                   ↑ 只是个字段名引用，不是表达式！
```
→ **嵌套 6 层，但里面全是简单引用**

**我失败的那版长这样：**

```sql
IIF(@查询维度='月',
    IIF(MAX(tm.c_task_sum) IS NULL OR MAX(tm.c_task_sum) = 0, NULL,
        CONVERT(VARCHAR(20), CAST(ROUND(
            ROUND(MAX(ss.c_sale_total) / MAX(tm.c_task_sum), 4) * 100, 1) AS DECIMAL(10,1))) + '%'),
    NULL) AS 月度任务完成率
--          ↑ 聚合 ÷ 聚合，埋在 5 层函数里
```

### 第 5 步：找到真正的规律

对比下来，**嵌套层数不是关键**（sqlA 有 6 层也能跑），真正的差别是：

| | 最外层 SELECT 里有什么 |
|---|---|
| sqlA（能跑） | `t.[月度任务完成率]` — **一个字段名** |
| sqlB 原版（能跑） | `SUM(a-b) / SUM(c)` — 简单聚合除法，3 层 |
| 我的失败版（报错） | `MAX(聚合) / MAX(聚合)`，埋在 5 层函数 + IIF 里 |

**→ 平台会深度解析最外层 SELECT 列表。里面越「干净」，越不容易挂。**

sqlA 之所以没事，是因为它**有两层结构**：内层算比率，外层只做格式化。平台
解析外层时看到的只是字段名，自然拆不坏。

## 三、解决公式

### 把「计算」全部挪进临时表，最外层 SELECT 只留「取值」

**改造前（报错）：**
```sql
SELECT
   ...
   IIF(@查询维度='月',
       IIF(MAX(tm.c_task_sum) IS NULL OR MAX(tm.c_task_sum) = 0, NULL,
           CONVERT(VARCHAR(20), CAST(ROUND(
               ROUND(MAX(ss.c_sale_total) / MAX(tm.c_task_sum), 4) * 100, 1) AS DECIMAL(10,1))) + '%'),
       NULL) AS 月度任务完成率
FROM ... GROUP BY ...
```

**改造后（通过）：**
```sql
-- ① 先建临时表，把比率、差值全算好
CREATE TABLE #ttb_calc (c_store_key VARCHAR(20), c_con_key VARCHAR(20),
                        c_sale_total DECIMAL(18,2), c_rate_m DECIMAL(18,6), ...)

INSERT INTO #ttb_calc (...)
SELECT k.c_store_key, k.c_con_key, k.c_sale_total,
       CASE WHEN ISNULL(m.c_task_sum,0)=0 THEN NULL
            ELSE ROUND(k.c_sale_total / m.c_task_sum, 4) END,
       ...
FROM (...) k
LEFT JOIN #ttb_task_m_sum m ON ...

-- ② 最外层 SELECT 只做「取值 + 简单格式化」
SELECT
   ...
   IIF(@查询维度='月',
       CONVERT(VARCHAR(20), CAST(ROUND(MAX(cc.c_rate_m) * 100, 1) AS DECIMAL(10,1))) + '%',
       NULL) AS 月度任务完成率
FROM ... LEFT JOIN #ttb_calc cc ON ...
GROUP BY ...
```

**差别就在**：`ROUND(MAX(a) / MAX(b), 4)` → `MAX(cc.c_rate_m)`

除法消失了，聚合没嵌套了，表达式一眼能看懂。

## 四、必做清单（写报表平台 SQL 时逐条对照）

### ✅ 可以做

| 写法 | 说明 |
|---|---|
| `SUM(a - b)` | 单层聚合 |
| `ROUND(SUM(x) / SUM(y), 2)` | 简单聚合除法，**3 层以内**，原 sqlB 就是这么跑的 |
| `MAX(临时表.算好的列)` | 从临时表取值，最安全 |
| 两层结构（内层算 / 外层格式化） | sqlA 的写法，平台认 |
| `CASE WHEN ... THEN ... END` 在**临时表 INSERT 里** | 平台不解析这里的深度 |

### ❌ 不要做

| 写法 | 后果 |
|---|---|
| `SUM(SUM(x)) OVER (PARTITION BY ...)` | 嵌套聚合 + 窗口，高风险 |
| 最外层 SELECT 里写 `ROUND(MAX(a)/MAX(b), 4)` 这种聚合间的除法 | **本次踩的坑** |
| `BETWEEN ... AND ...` 写在 JOIN 的 ON 里 | 平台可能按 `AND` 拆分条件 |
| 最外层 SELECT 里堆 5 层以上函数嵌套 | 越深越危险 |
| 在 `GROUP BY` 末尾加额外的辅助列 | 本次也回退掉了，保持和原版逐字一致 |

### 🔧 三个动作

1. **先跑通最简版**：只加 1 个新列，确认能跑，再逐个加。哪列挂就是哪列的表达式有问题
2. **改完一次报错一模一样 → 立刻换方向**，别再在同一个地方打转
3. **`GROUP BY` 保持和原版逐字一致**，不要为了新逻辑去动它

## 五、如果以后又遇到：5 分钟定位流程

```
① Navicat 能跑？
   否 → 改 SQL
   是 ↓
② 报错里的 ")" / 关键字 数量，和你的括号配平数对得上吗？
   对不上 → 平台拆坏了，跳到 ④
③ 最近改了什么？把改动整体注释掉，确认是不是新代码引起的
④ 查最外层 SELECT 列表：
   - 有没有嵌套聚合？
   - 有没有 MAX(a) / MAX(b) 这种聚合间除法？
   - 有没有 5 层以上函数嵌套？
   - 有 → 全部挪进临时表，最外层只留 MAX(临时表.列)
⑤ GROUP BY 有没有意外增加/减少项？恢复成原版
```

## 七、一句话记住

> **平台 SQL 的最外层 SELECT，是给「人看」的，不是给「计算器」用的。**
> 所有计算提前在临时表做完，最外层只留 `MAX(列名)` 和简单格式转换。
